MulticastIntroduction to group communications in TCP/IP networks

Muitas aplicações servem não um utilizador, mas um grupo: transmissões de vídeo, videoconferências, distribuição de atualizações. Podem precisar de comunicação ponto-a-ponto, ponto-a-multiponto ou multiponto-a-multiponto.

5.0.1Porque não vários unicast?

Os pacotes IP são normalmente enviados de uma fonte para um destino. Para chegar a vários, a fonte podia enviar um unicast a cada um — mas isso obriga a:

  • a fonte manter a lista completa de destinatários;
  • enviar várias cópias idênticas dos mesmos dados.

É uma solução cara em processamento e em transmissão. Daí o multicast.

5.0.2A ideia

  • Enviar uma única cópia dos dados para um grupo de destinatários, identificado por um endereço multicast — uma abstração: a fonte não precisa de saber quem está no grupo.
  • Os nós da rede (routers, se for ao nível da rede) encaminham os pacotes e duplicam-nos só quando é preciso, onde os caminhos se separam.
Complemento · endereços multicast

Em IPv4 os endereços multicast são os da antiga classe D, 224.0.0.0/4 (224.0.0.0 a 239.255.255.255); em IPv6 começam por ff00::/8. Os conceitos do tema aplicam-se também a multicast ao nível da aplicação.

5.0.3As duas peças

Entre hosts e router

Os hosts usam protocolos de descoberta de membros (IGMP em IPv4, MLD em IPv6) para dizer ao router local que querem receber dados de um grupo.

Entre routers

Os routers usam protocolos de encaminhamento multicast para construir uma árvore de distribuição: o tráfego chega a todos os membros do grupo com o mínimo de cópias.

Descoberta de membros: IGMP e MLDMulticast Group Membership Discovery Protocols

Os hosts usam estes protocolos para dizer aos routers da sua LAN o endereço do grupo multicast a que querem aderir: IGMP (Internet Group Management Protocol) em IPv4 e MLD (Multicast Listener Discovery) em IPv6.

5.1.1Funcionamento básico do IGMP

  1. Um host que quer aderir a um grupo envia um IGMP Report não solicitado para esse grupo.
  2. Um router local apanha o Report e usa um protocolo de encaminhamento multicast para se juntar ao grupo.
  3. Periodicamente, um router querier envia IGMP Query em broadcast, para saber a que grupos estão subscritos os hosts locais.
  4. Os hosts respondem com IGMP Reports a indicar os grupos de que são membros.
  5. Se o router deixar de receber Reports de um grupo durante algum tempo, assume que já não há membros na LAN e sai do grupo.

5.1.2Evitar respostas em avalanche

Para que muitos hosts não respondam ao mesmo tempo, cada host arranca um temporizador aleatório por cada grupo de que é membro. Quando o temporizador acaba, envia o Report — mas se entretanto ouvir um Report de outro host para o mesmo grupo, cancela o seu. Ao router basta saber que há pelo menos um membro.

5.1.3As versões

VersãoO que acrescenta

Alternativas de desenhoDesign alternatives

Três decisões definem um protocolo de multicast: de que fontes se recebe, como se constrói a árvore e que tipo de árvore se usa.

5.2.1De que fontes: ASM vs. SSM

ASM · Any Source Multicast

O host indica só o grupo e recebe dados enviados para ele por qualquer fonte.

SSM · Source-Specific Multicast

O host indica o grupo e a fonte: só recebe dados daquela fonte.

5.2.2Como construir a árvore: opt-in vs. opt-out

Opt-in

Os nós indicam os grupos que lhes interessam; a árvore constrói-se a partir dos joins dos clientes. Ex.: PIM-SM.

Opt-out (flood and prune)

Assume-se que todos os nós querem os dados; depois, os que não têm clientes interessados cortam-se (prune) da árvore. Ex.: PIM-DM.

Numa árvore partilhada unidirecional (como no PIM-SM), o router da fonte encapsula cada pacote, envia-o ao RP em unicast, e o RP desencapsula-o e distribui-o pela árvore.

5.2.4Descobrir o router a montante: RPF

Os protocolos precisam de saber qual é a interface a montante (em direção à fonte ou ao RP). Usam o algoritmo Reverse Path Forwarding (RPF). Essa interface serve:

  • como interface de saída para as mensagens de controlo (join, leave, prune…);
  • como a única interface de entrada aceite para os dados multicast: se um pacote chegar por outra interface, é descartado — evita duplicados e ciclos.

O PIM faz as consultas RPF numa Multicast Routing Information Base (MRIB), parecida com uma tabela de encaminhamento unicast.

Protocol Independent MulticastPIM Sparse Mode · PIM Dense Mode

O PIM é o protocolo de encaminhamento multicast mais usado. "Independente do protocolo" porque não depende do protocolo de encaminhamento unicast da rede: usa a informação que já existe (a MRIB). Tem dois modos principais.

5.3.1PIM Sparse Mode (PIM-SM)

Protocolo opt-in: só encaminha o tráfego multicast depois de um router a jusante o pedir. É o mais usado em ambientes "esparsos", onde poucas partes da rede querem cada grupo.

  1. Os hosts indicam interesse com IGMP ou MLD.
  2. Um dos routers da LAN é eleito Designated Router (DR): é ele que se junta ao grupo e encaminha o tráfego.
  3. Os routers enviam PIM (*, G) Join em direção ao RP, criando estado de encaminhamento pelo caminho: a Rendezvous Point Tree (RPT).
  4. Os dados de uma fonte chegam ao RP encapsulados em unicast, e daí descem pela árvore partilhada.
  • Por omissão usa árvores partilhadas com raiz no RP, mas também suporta árvores por fonte: para evitar o encapsulamento, para otimizar o caminho dos dados e para o SSM.
  • É um protocolo de soft state: o estado expira algum tempo depois das mensagens de controlo, por isso os joins são reenviados periodicamente para o manter.
Vantagens
  • Independente do protocolo unicast da rede.
  • Escala bem.
  • Suporta SSM e ASM.
  • Árvores partilhadas (sem estado por fonte) e por fonte (caminhos mais eficientes).
Desvantagens
  • As árvores partilhadas exigem encapsulamento/desencapsulamento entre a fonte e o RP.
  • É preciso um mecanismo para levar os dados da fonte ao RP.

5.3.2PIM Dense Mode (PIM-DM)

Protocolo opt-out (flood and prune), só com árvores por fonte. Assume que a maior parte das redes do domínio quer receber os dados, por isso encaminha para todas as interfaces até que um router a jusante peça para parar. Usado em domínios pequenos e redes com poucos recursos.

  1. Inundação: os dados são enviados para toda a rede — mas cada router verifica se o pacote chegou pela interface mais próxima da fonte (RPF); se não, descarta-o.
  2. Prune: um router que não precisa dos dados envia uma mensagem PIM (S, G) Prune a montante, e o router a montante deixa de lhe enviar.
  3. O estado de prune expira: os dados voltam a chegar às zonas cortadas, que voltam a fazer prune — ou aceitam, se agora houver interesse.
  4. Graft: se aparecer um recetor numa zona cortada, o router local envia um PIM (S, G) Graft a montante para voltar a entrar na árvore. O graft é confirmado com um acknowledgment explícito — o único caso no PIM.
Vantagens
  • Eficiente quando os recetores estão densamente distribuídos.
  • Evita a complexidade de configurar um RP.
Desvantagens
  • Todos os routers guardam estado por fonte, para todas as fontes do domínio.
  • Não escala em domínios onde a maioria não quer os dados.

Σ.2Perguntas de escolha múltipla

Que protocolo usa um host IPv4 para aderir a um grupo multicast?

IGMP em IPv4, MLD em IPv6. O PIM é entre routers.

Que versão do IGMP introduz a mensagem Leave Group?

O IGMPv2 traz o Leave e a eleição do querier; o v3 traz a filtragem por fonte.

Um router envia um Join (*, G). Que árvore está a usar?

(*, G) = qualquer fonte do grupo G, pela árvore partilhada. (S, G) indica uma fonte concreta.

Um router recebe um pacote multicast por uma interface que não é a que leva à fonte. O que faz?

O RPF evita duplicados e ciclos.

Qual é o único caso no PIM em que há acknowledgment explícito?

O Graft (voltar a entrar numa zona cortada) é confirmado explicitamente.

Num domínio grande onde poucos routers têm recetores, qual escolhes?

O PIM-DM inundaria todo o domínio e obrigaria todos os routers a guardar estado por fonte.

Porque é que o SSM exige árvores por fonte?

Numa árvore partilhada não se distingue a fonte; no SSM a adesão já indica a fonte.

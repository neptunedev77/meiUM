Camada de Aplicação: PrincípiosApplication Layer · Principles of network applications

A camada de aplicação é onde vivem os serviços que usamos: Web, email, streaming, jogos, videochamadas. Este tema trata dos conceitos comuns a todas estas aplicações — como se organizam, como os processos comunicam e o que precisam da rede.

1.0.1Uma variedade enorme de aplicações

Email, Web, mensagens, acesso remoto, partilha de ficheiros P2P, jogos multijogador, streaming de vídeo, voz sobre IP, videoconferência em tempo real, redes sociais, pesquisa… A Internet suporta todas, com características e requisitos de qualidade muito diferentes.

1.0.2Criar uma aplicação de rede

  • Escrever programas que correm em sistemas terminais (diferentes) e comunicam pela rede — ex.: o software do servidor web comunica com o browser.
  • Não é preciso escrever software para os equipamentos do núcleo da rede (routers, switches): esses não correm aplicações de utilizador.
  • Ter as aplicações nos sistemas terminais permite desenvolvê-las e espalhá-las depressa.
Princípio extremo-a-extremo (end-to-end)

A inteligência das aplicações fica nas extremidades da rede (os sistemas terminais); o núcleo limita-se a encaminhar pacotes. É por isso que se pode lançar uma aplicação nova sem pedir autorização a ninguém nem alterar um único router. complemento

Arquiteturas de aplicaçõesClient-server · Peer-to-peer

Há duas formas principais de estruturar uma aplicação: cliente-servidor e peer-to-peer (P2P).

Cliente-servidor

Servidor:

  • host sempre ligado;
  • endereço IP permanente;
  • data centers para escalar.

Clientes:

  • comunicam com o servidor;
  • podem estar ligados de forma intermitente;
  • podem ter IP dinâmico;
  • não comunicam diretamente uns com os outros.
Peer-to-peer (P2P)
  • Sem servidor sempre ligado (no P2P puro).
  • Sistemas terminais arbitrários comunicam diretamente.
  • Os peers pedem serviço a outros peers e, em troca, prestam serviço a outros peers.
  • Autoescalabilidade: cada peer novo traz nova procura, mas também nova capacidade de serviço.
  • Os peers ligam-se de forma intermitente e mudam de IP → gestão complexa.

O tema 2 aprofunda o P2P, incluindo uma comparação quantitativa entre as duas arquiteturas.

Processos, sockets e endereçamentoProcesses communicating · Sockets · Addressing

Na rede não comunicam computadores: comunicam processos.

1.2.1Processos

  • Processo: um programa a correr num host.
  • No mesmo host, dois processos comunicam por mecanismos de comunicação entre processos (definidos pelo SO).
  • Em hosts diferentes, comunicam trocando mensagens.
  • Processo cliente: o que inicia a comunicação. Processo servidor: o que espera ser contactado.
  • Mesmo em P2P há processos clientes e processos servidores — um peer faz os dois papéis.

1.2.2Sockets

O processo envia e recebe mensagens através do seu socket, que funciona como uma porta: o processo empurra a mensagem porta fora e confia na infraestrutura de transporte do outro lado para a entregar ao socket do processo destino.

CamadaControlada por
Aplicação (processo) — acima do socketQuem desenvolve a aplicação
Transporte, rede, ligação, física — abaixo do socketO sistema operativo

Os sockets usam um protocolo de transporte: TCP (stream), UDP (datagram) ou até sockets raw, que dão acesso direto a protocolos de mais baixo nível (como o ICMP).

1.2.3Endereçar processos

Para receber mensagens, um processo precisa de um identificador. O endereço IP do host (32 bits em IPv4) chega? Não: podem correr muitos processos no mesmo host.

Identificador de um processo
\[\text{endereço IP} + \text{número de porta}\]
Portas bem conhecidas
  • Servidor HTTP: 80
  • Servidor de email (SMTP): 25
Exemplo

Mensagem HTTP para o servidor web de gaia.cs.umass.edu: IP 128.119.245.12, porta 80.

1.3.1Temas que se repetem em todos os protocolos

  • Troca típica de pedido/resposta: o cliente pede informação ou um serviço; o servidor responde com dados e um código de estado.
  • Formato das mensagens: cabeçalhos (campos que descrevem os dados) + dados (o payload que se comunica).
  • Mensagens de controlo vs. dados: na mesma ligação (in-band) ou numa ligação separada (out-of-band).
  • Centralizado vs. descentralizado.
  • Sem estado vs. com estado (stateless vs. stateful).
  • Transferência de mensagens fiável vs. não fiável.
  • A complexidade fica na periferia da rede.

Que serviço de transporte precisa uma aplicação?Transport service requirements

Aplicações diferentes precisam de coisas diferentes da rede. Quatro dimensões resumem essas necessidades.

Integridade dos dados

Algumas aplicações (transferência de ficheiros, transações web) exigem transferência 100% fiável; outras (áudio) toleram alguma perda.

Débito (throughput)

Algumas (multimédia) precisam de um débito mínimo para serem eficazes; outras — as elásticas — usam o que houver.

Temporização

Algumas (telefonia na Internet, jogos interativos) precisam de atraso baixo para serem eficazes.

Segurança

1.4.1TCP vs. UDP

ServiçoTCPUDP
Transporte fiável entre processos✓✗
Controlo de fluxo (o emissor não afoga o recetor)✓✗
Controlo de congestão (abranda quando a rede está sobrecarregada)✓✗
Orientado à conexão (é preciso estabelecer a ligação)✓✗
Temporização, débito mínimo garantido, segurança✗✗
Então porque é que existe o UDP?

Precisamente porque não faz nada disto: sem estabelecimento de ligação (menos atraso), sem controlo de congestão (a aplicação envia ao ritmo que quiser) e cabeçalhos mais pequenos. Para voz, vídeo em tempo real ou jogos, chegar a tempo vale mais do que chegar tudo; e protocolos como o QUIC constroem a sua própria fiabilidade por cima do UDP. complemento

1.4.3Segurança: TLS

  • Sockets TCP e UDP "simples" não cifram: uma password enviada para o socket atravessa a Internet em claro.
  • O TLS (Transport Layer Security) fornece ligações TCP cifradas, integridade dos dados e autenticação dos extremos.
  • O TLS é implementado na camada de aplicação: as aplicações usam bibliotecas TLS, que por sua vez usam TCP. O texto que a aplicação escreve no "socket" TLS atravessa a Internet cifrado.

Σ.2Perguntas de escolha múltipla

Porque é que o endereço IP não basta para identificar um processo?

IP + porta identifica o processo dentro do host.

Qual destas afirmações sobre cliente-servidor é verdadeira?

A autoescalabilidade é característica do P2P; em cliente-servidor os clientes só falam com o servidor.

Uma aplicação "elástica" é uma aplicação que…

Ex.: email, transferência de ficheiros, Web.

Que serviço o TCP não fornece?

Nem TCP nem UDP garantem temporização, débito mínimo ou segurança.

Onde é implementado o TLS?

A aplicação usa uma biblioteca TLS, que cifra os dados antes de os passar ao TCP.

Em que protocolo de transporte assenta o HTTP/3?

As versões anteriores do HTTP usam TCP; o HTTP/3 usa QUIC, que corre sobre UDP.

Introdução: DevOps e Infraestrutura como CódigoIntroduction

Uma aplicação real raramente é um programa num servidor. É um conjunto de componentes — servidores web, bases de dados, filas de mensagens, sistemas de armazenamento — espalhados por muitas máquinas. Esta UC trata de como se desenham, instalam, configuram e operam sistemas assim.

1.0.1Uma aplicação "simples"

Mesmo uma aplicação web pequena já tem várias peças: o browser fala com um servidor web, que passa os pedidos a um servidor aplicacional, que lê e escreve numa base de dados. Cada peça tem as suas dependências, a sua configuração e pode falhar de forma independente.

  2. Servidor web

1.0.2Aplicações e infraestruturas complexas

Nas grandes empresas a escala é outra:

Pipelines de dados

A Netflix recolhe eventos de milhões de dispositivos e encaminha-os, através de filas de mensagens e processamento em streaming, para vários sistemas de armazenamento e análise (pipeline Keystone).

Motores de consulta

O Presto, do Facebook, executa consultas SQL sobre petabytes de dados guardados em vários backends diferentes, distribuindo o trabalho por muitos servidores.

Bases de dados distribuídas

O HBase espalha os dados por muitos servidores, apoia-se num sistema de ficheiros distribuído e num serviço de coordenação.

E por baixo estão infraestruturas igualmente complexas: centenas ou milhares de servidores com hardware heterogéneo, serviços de cloud e de computação de alto desempenho (HPC) a funcionar em conjunto.

Os desafiosChallenges

Ter muitos componentes em muitas máquinas cria três grandes problemas.

Deployment
  • As aplicações têm vários componentes, com requisitos diferentes (hardware, bibliotecas…).
  • O hardware, o software e os serviços são heterogéneos (serviços de cloud, serviços de HPC…).
Gestão e configuração
  • A configuração é específica de cada componente de software e de hardware.
  • A configuração ótima muda com o tempo (carga, versões, hardware novo).
Monitorização e benchmarking
  • Encontrar anomalias — de desempenho, falhas… — em aplicações e infraestruturas complexas.
  • Medir o desempenho para saber se o sistema cumpre o que se espera dele.
A ideia que atravessa a UC

Fazer estas tarefas à mão não escala. A resposta é automatizar: descrever a infraestrutura e a sua configuração em código, versioná-lo e aplicá-lo com ferramentas. É o caminho deste tema: do desenvolvimento ágil à infraestrutura como código e ao DevOps.

Desenvolvimento ágilAgile development

No desenvolvimento de software, o processo já é cíclico e automatizado: requisitos viram código, o código vira binários, os binários são lançados, os problemas encontrados alimentam novos requisitos — e repete-se.

… e volta-se aos requisitos: iterar.

1.2.1Em que assenta

  • Repositórios formais e versionados de código, binários e documentação:
    • um estado atual inequívoco — toda a gente sabe o que está em produção;
    • a possibilidade de voltar atrás.
  • Build e testes automáticos: feedback rápido sobre cada alteração.
  • Iterações rápidas: reagir depressa a alterações pequenas e frequentes.

A pergunta do tema é: e a infraestrutura onde o software corre? Também segue este processo?

Operações tradicionaisOperations

Do lado das operações, o fluxo tradicional é: provisionar hardware, SO e plataforma, configurar, fazer um teste de qualificação e depois repetir tudo em produção, onde o sistema é monitorizado.

  1. Provisionar
  2. Configurar
  3. Teste de qualificação
  4. Provisionar
  5. Configurar
  6. Produção
  7. Monitorizar

1.3.1O problema

  • O provisionamento e a configuração são manuais.
  • A comunicação entre a fase de qualificação e a de produção é informal ("instalei isto e mudei aquilo…").

1.3.2As consequências

ConsequênciaO que significa
Não repetível nem reprodutívelNinguém sabe exatamente que passos levaram o servidor ao estado atual; refazê-lo noutro sítio dá um resultado diferente.
Configuration driftCom o tempo, pequenas alterações manuais fazem os servidores divergir uns dos outros e do que estava documentado.
Servidores "snowflake"Cada servidor fica único, como um floco de neve: tão frágil e desconhecido que ninguém lhe quer mexer ("nem olhes para ele…").
Monitorização subjetivaSem um estado de referência, "está a funcionar bem?" passa a ser uma opinião.

Infraestrutura como códigoInfrastructure as Code (IaC)

A ideia é tratar a infraestrutura como se trata o software: descrevê-la em scripts, guardá-los num repositório e aplicá-los automaticamente.

TarefaCom IaCEm vez de…
Provisionar hardwareScripts que pedem máquinas, discos e redesDesembalar, ligar e configurar fisicamente
Provisionar softwareScripts que instalam pacotes e aplicaçõesClicar em assistentes de instalação
ConfigurarScripts que escrevem ficheiros de configuração e ativam serviçosClicar em painéis de controlo

E, sobretudo: incluir os scripts de infraestrutura no processo ágil — versionados, revistos e testados como o resto do código.

#!/bin/sh
username=deployer
apt-get -y update
apt-get -y install vim-nox openntpd sudo
useradd -G sudo -s /bin/bash -m $username
mkdir -p /home/$username/.ssh
echo "public_key" >> /home/$username/.ssh/authorized_keys
Complemento · imperativo vs. declarativo

Um script como o de cima é imperativo: diz os passos a dar. Corrido duas vezes, acrescenta a chave duas vezes. As ferramentas de gestão de configuração (tema 3) são sobretudo declarativas: descreve-se o estado final desejado ("o utilizador existe, a chave está autorizada") e a ferramenta só age se o estado atual for diferente.

DevOpsDevOps

Desenvolvimento ágil + infraestrutura como código = DevOps. O ciclo de desenvolvimento passa a incluir também a infraestrutura: ao lado do código e dos binários, versionam-se os scripts e as imagens das máquinas.

  1. Requisitos
  2. Código + scripts
  3. Binários + imagens
  4. Release
  5. Issues

1.5.1O que se ganha

  • O desenvolvimento e o deployment ficam autodocumentados e versionados.
  • O deployment é reprodutível e repetível.
  • Os servidores são descartáveis e consistentes: se um avaria ou diverge, destrói-se e recria-se a partir dos scripts.
  • Suporta alterações rápidas, frequentes e pequenas.
Operações tradicionaisDevOps
Provisionamento e configuraçãoManuaisScripts versionados
Passagem qualificação → produçãoComunicação informalOs mesmos scripts nos dois ambientes
ServidoresÚnicos ("snowflakes")Descartáveis e iguais entre si
Reproduzir um ambienteDifícil ou impossívelCorrer os scripts outra vez
Complemento · "pets vs. cattle"

Uma metáfora comum: servidores tradicionais são animais de estimação (têm nome, trata-se deles quando adoecem); servidores em DevOps são gado (são numerados e, se um falha, substitui-se).

Classifica cada prática:

Entrar por SSH no servidor de produção e editar o ficheiro de configuração à mão.
Alterar o template de configuração no Git e aplicá-lo com uma ferramenta a todos os servidores.
Um servidor comporta-se de forma estranha: destrói-se e cria-se outro a partir da imagem.
Enviar à equipa de produção um email com os passos que se fizeram no servidor de testes.

Σ.2Perguntas de escolha múltipla

O que é um servidor "snowflake"?

Como um floco de neve, é único: resultado de alterações manuais não registadas (configuration drift).

DevOps resulta da combinação de…

Leva o processo ágil (versionado, automatizado, iterativo) também à infraestrutura.

Qual destas é uma consequência do provisionamento manual?

Alterações manuais acumulam-se e fazem os servidores divergir. As outras opções são vantagens do DevOps.

Em DevOps, o que se versiona além do código e dos binários?

Scripts e imagens permitem recriar o ambiente de forma idêntica.

Porque é que, em DevOps, os servidores podem ser "descartáveis"?

Com a infraestrutura em código, recriar um servidor é correr os scripts outra vez.

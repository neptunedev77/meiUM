ArmazenamentoStorage

Bases de dados, analytics, machine learning, a cloud, a computação de alto desempenho (HPC), a IoT: todos assentam num sistema de armazenamento. É ele que garante que os dados persistem e estão disponíveis.

7.0.1O desempenho conta

Guardar e ler dados devagar dá aplicações e serviços lentos. Por isso, não há um armazenamento "certo": há o adequado a cada tipo de uso, com um meio, uma interface, uma escala e um conjunto de funcionalidades próprios. O tema percorre essas cinco perguntas e termina numa forma de as combinar com flexibilidade: o Software-Defined Storage.

Para quê?

Arquivo, backup ou dados primários.

Onde e como?

Fita, HDD, SSD, memória; bloco, ficheiro ou objeto.

A que escala?

Um disco, um servidor, um centro de dados, milhões de nós.

Ordens de grandeza complemento

Latência típica de um acesso aleatório: RAM ≈ 100 ns; SSD NVMe ≈ 10–100 µs; HDD ≈ 5–10 ms (o braço tem de se mover e o disco de rodar); fita: segundos a minutos (é preciso montar e enrolar a fita). Entre a RAM e o HDD há um fator de cerca de 100 000. É por isso que o padrão de acesso (sequencial ou aleatório) pesa tanto na escolha do meio, e porque é que as caches valem tanto.

Interfaces de armazenamentoStorage Interfaces

A mesma informação pode ser apresentada a quem a usa de três formas diferentes, com níveis de abstração diferentes.

Bloco

Os dados são um conjunto de blocos numerados: é a abstração mais próxima do disco.

Ex.: block device Linux, iSCSI, Amazon EBS, Ceph

Sistema de ficheiros

Uma hierarquia de ficheiros e diretorias: a abstração que a maioria das pessoas usa no seu computador.

Ex.: Ext4, NFS, HDFS, Lustre, Ceph

Objeto

Os dados são objetos, por exemplo um par chave-valor por ficheiro: a chave é um identificador único e o valor o conteúdo.

Ex.: Amazon S3, OpenStack Swift, Ceph

O Ceph aparece nas três colunas: é um sistema distribuído que oferece as três interfaces sobre o mesmo armazenamento.

Na prática complemento
  • Bloco: quem o usa tem de pôr por cima um sistema de ficheiros ou uma base de dados. É o "disco" de uma VM.
  • Ficheiro: caminhos, permissões, operações POSIX (abrir, ler, escrever num deslocamento, renomear).
  • Objeto: um espaço de nomes plano, acedido por HTTP (PUT, GET, DELETE de objetos inteiros), com metadados à medida e escala praticamente ilimitada. Não se altera "um bocado" de um objeto: substitui-se. É ideal para backups, media e dados de analytics, e pouco adequado a uma base de dados.

Do local ao peer-to-peerStorage Scope

O mesmo pedido de uma aplicação, "lê os bytes deste ficheiro", pode ser servido por um disco local, por um servidor na rede, por um cluster com centenas de servidores ou por milhões de nós.

7.4.1Local

O sistema operativo faz de intermediário entre os pedidos de I/O das aplicações e os discos locais, através das chamadas ao sistema.

  • As aplicações podem falar diretamente com a camada de blocos (uma base de dados que gere o disco sozinha), ou com um sistema de ficheiros (ext4, ZFS, XFS).
  • O VFS (Virtual File System) dá uma interface e uma abstração comuns: cada sistema de ficheiros implementa essa abstração, especializando-a para as suas necessidades.
  • A page cache do SO guarda em memória o conteúdo dos ficheiros, para acessos mais rápidos.

7.4.2Remoto

O armazenamento é oferecido através da rede, seja como dispositivo de blocos (iSCSI) ou como sistema de ficheiros (NFS), numa arquitetura cliente-servidor. No cliente, os pedidos de I/O são intercetados (no caso do NFS, pela especialização NFS do VFS) e enviados pela rede. No servidor, são entregues ao componente servidor (o servidor NFS), que os guarda no seu disco local. Para a aplicação, tudo parece local.

7.4.3Distribuído (centro de dados)

Na cloud e em HPC, dezenas a centenas de servidores guardam os dados: HDFS, Ceph, Lustre, GPFS.

  • Sem ponto único de falha: os dados estão distribuídos, replicados ou particionados (sharding), pelos nós de dados.
  • Os metadados (onde está cada ficheiro, permissões) são geridos por nós de metadados independentes.
  • O cliente pergunta aos nós de metadados onde estão os dados, e depois lê-os ou atualiza-os diretamente nos nós de dados. Os metadados não se tornam um gargalo para o tráfego de dados.
  • É um desenho gestor-trabalhador, otimizado para um churn estável: servidores a falhar a um ritmo baixo e previsível.

7.4.4Altamente distribuído (peer-to-peer)

Milhares a milhões de nós, por exemplo numa infraestrutura de IoT: Napster, Gnutella, CFS, DataFlasks.

  • Dados e metadados replicados por muitos nós, sem nós especializados.
  • As aplicações podem fazer pedidos a qualquer nó.
  • É difícil manter uma visão consistente em todos os nós: garantir que clientes ligados a nós diferentes, ao mesmo tempo, veem os mesmos ficheiros e o mesmo conteúdo.
  • Desenho P2P, otimizado para churn alto: espera-se que os nós falhem e voltem com frequência.

FuncionalidadesStorage Features

Por cima do armazenamento em si, os sistemas oferecem funcionalidades com quatro objetivos: disponibilidade, desempenho, eficiência de espaço e segurança.

7.5.1Disponibilidade

RAID

Redundant Array of Inexpensive Drives: dados replicados ou repartidos por vários discos de um só servidor, para disponibilidade e para repartir a carga.

Replicação

Cópias exatas em vários servidores. Fator 3: aguenta 2 falhas, com 3× o espaço.

Erasure codes

Os dados dividem-se em k blocos, a que se juntam m blocos de paridade, espalhados por servidores. Reed-Solomon (6, 3): aguenta 3 falhas, com só 1.5× o espaço.

Custo em espaço e falhas toleradas
\[\text{replicação }r:\ \ r\times,\ \ r-1\text{ falhas}\qquad\text{erasure code }(k,m):\ \ \frac{k+m}{k}\times,\ \ m\text{ falhas}\]
Então porque não usar sempre erasure codes? complemento

Para ler os dados quando falta um fragmento, é preciso ir buscar k fragmentos a k servidores e recalcular. Isso custa rede e CPU, e aumenta a latência. Por isso é comum replicar os dados "quentes" (acedidos muitas vezes) e usar erasure codes para os "frios": backups e arquivo.

7.5.2Desempenho

Localidade dos dados

Levar a computação para perto dos dados: processar no mesmo servidor ou dispositivo onde os dados estão guardados, o que torna o acesso mais rápido. Ex.: HBase sobre HDFS, active storage.

Cache

Manter os dados perto do cliente, ou numa fonte mais rápida (RAM), para não esperar pelo armazenamento local ou remoto. Ex.: a page cache do sistema de ficheiros, o Alluxio (sistema de ficheiros distribuído em memória).

7.5.3Eficiência de espaço

Compressão

Remove conteúdo redundante (bytes) dentro de ficheiros e entre eles. Usa-se sobretudo como técnica estática: em conjuntos de ficheiros que não vão ser alterados.

Deduplicação

Elimina cópias redundantes (de ficheiros ou blocos) no sistema de armazenamento, guardando cada uma só uma vez. É uma técnica dinâmica: funciona com ficheiros e blocos que vão continuar a ser atualizados.

7.5.4Segurança

  • Cifra em repouso: os dados são cifrados antes de serem guardados.
  • Cifra em trânsito: os dados são cifrados antes de atravessarem a rede, nos sistemas de armazenamento remotos.
  • Controlo de acesso: impedir acessos não autorizados aos dados dos utilizadores.
Cifrar em trânsito vs. no cliente complemento

Na prática, "em trânsito" costuma significar proteger a ligação (TLS): os dados são decifrados quando chegam ao servidor. Se forem cifrados no próprio cliente e só ele tiver a chave, nem o fornecedor do armazenamento os consegue ler: é a client-side encryption, a proteção mais forte. O preço é que o servidor deixa de conseguir comprimir ou deduplicar esses dados, porque os dados cifrados parecem aleatórios.

Software-Defined Storage

Num centro de dados, um pedido de I/O atravessa uma pilha longa: a aplicação, o sistema de ficheiros local, a VM, o armazenamento remoto, os discos. Cada camada oferece uma combinação fixa de funcionalidades. Mas a melhor combinação depende da aplicação.

7.6.1O problema

O que convém a uma aplicação não convém a outra: ficheiros pequenos ou grandes, padrões de acesso diferentes, informação sensível ou não. Uma solução monolítica e complexa, com as mesmas funcionalidades para todos, é demasiado rígida.

7.6.2Os princípios

  • Os fluxos de I/O (plano de dados) estão separados do fluxo de controlo (plano de controlo).
  • O plano de controlo tem o controlo global dos fluxos de I/O, de forma logicamente centralizada.

7.6.3Plano de dados

  • Organizado em camadas, com estágios.
  • Cada estágio trata os pedidos no caminho de I/O e oferece uma funcionalidade: cache, compressão, cifra…
  • É programável e extensível: podem acrescentar-se estágios com novas funcionalidades.

7.6.4Plano de controlo

  • Tem uma visão global das aplicações, dos estágios e dos recursos da infraestrutura: é o "cérebro" que coordena o conjunto.
  • É distribuído, para escalar e para estar sempre disponível.
  • Configura e afina os estágios para impor políticas de I/O:
    • qualidade de serviço: equidade entre aplicações, ou prioridades;
    • transformações: cifra, compressão.
  • As políticas são definidas através de aplicações de controlo.

Exemplo: uma política diz "os ficheiros da aplicação de saúde são cifrados; o backup noturno não pode tirar mais de 30% do débito à base de dados". O plano de controlo liga o estágio de cifra no caminho da primeira e limita o débito do segundo, sem mudar nenhuma das aplicações.

A mesma ideia nas redes complemento

O SDS segue o modelo das Software-Defined Networks (SDN), onde os switches só encaminham pacotes (plano de dados) e um controlador central decide as regras (plano de controlo). Em ambos, separar o "fazer" do "decidir" torna a infraestrutura programável.

Σ.2Exercícios

1. Quer guardar 200 TB tolerando a falha de quaisquer 2 servidores. Quanto espaço bruto precisa com replicação, e com um erasure code (10, 2)?

Replicação: para aguentar 2 falhas é preciso r = 3, ou seja 600 TB. Erasure code (10, 2): aguenta m = 2 falhas com (10 + 2) / 10 = 1.2×, ou seja 240 TB. Poupam-se 360 TB, à custa de reconstruções mais caras quando há falhas.

2. Um código Reed-Solomon (k = 6, m = 3): quantos fragmentos, quantos servidores podem falhar, e qual é o custo em espaço?

9 fragmentos (6 de dados + 3 de paridade), em 9 servidores; aguenta 3 falhas; ocupa 9/6 = 1.5× o espaço original.

3. Num sistema de ficheiros distribuído, porque é que o cliente lê os dados diretamente dos nós de dados, e não através dos nós de metadados?

Para que os nós de metadados não se tornem um gargalo: só respondem a perguntas pequenas ("onde está o ficheiro A?"), enquanto o tráfego pesado (o conteúdo) vai em paralelo para os nós de dados.

4. Para backups diários de uma pasta que muda pouco de um dia para o outro, compressão ou deduplicação?

Sobretudo deduplicação: a maior parte dos blocos repete-se de um backup para o seguinte e só se guarda uma vez, mesmo que os ficheiros continuem a mudar. As duas técnicas também se combinam: comprimem-se os blocos únicos.

Σ.3Perguntas de escolha múltipla

O que caracteriza uma carga de trabalho de arquivo?

Os dados de arquivo escrevem-se uma vez e raramente se leem. Um exemplo na cloud é o Amazon Glacier.

Uma base de dados transacional precisa sobretudo de…

Escritas e leituras pequenas, aleatórias e frequentes. O armazenamento de objetos substitui objetos inteiros e não é adequado a isto.

Qual destas é uma interface de armazenamento de blocos?

O NFS é um sistema de ficheiros remoto; o S3 é armazenamento de objetos.

Qual é o papel do VFS no kernel?

Guardar os ficheiros em memória é o papel da page cache; falar com o disco cabe ao driver.

Num sistema de ficheiros distribuído como o HDFS ou o Ceph, como se acede a um ficheiro?

Todos os nós serem iguais é o desenho P2P, pensado para churn alto.

O custo escondido do erasure code está na reconstrução: ler k fragmentos e recalcular.

Qual é a diferença entre compressão e deduplicação, tal como são usadas habitualmente?

A deduplicação elimina cópias repetidas de ficheiros ou blocos em todo o sistema.

Processar os pedidos é o papel do plano de dados, nos seus estágios.

Virtualização: ContentoresVirtualization (Part II)

Um contentor é um ambiente virtual leve que agrupa e isola um conjunto de processos e recursos (memória, CPU, disco…), tanto do host como de outros contentores.

6.0.1Porque são úteis

Versões isoladas

Correr versões diferentes do mesmo software (ex.: duas versões de uma base de dados) sobre o mesmo SO e kernel, sem conflitos.

Portabilidade

Mover ou migrar a aplicação entre servidores.

Empacotamento

Juntar a aplicação e as suas dependências num único pacote, fácil de distribuir.

O tema segue três níveis: o mecanismo (contentores Linux), a ferramenta para um servidor (Docker) e o orquestrador para muitos servidores (Kubernetes).

⌁Mapa do tema

Baseado nas aulas de ASCN (Virtualization, Part II). Caixas e etiquetas complemento vão além da matéria dada na aula.

Contentores LinuxLinux Containers

Os contentores são leves porque não virtualizam por completo o CPU, a RAM, a rede e o armazenamento, ao contrário das VMs: partilham o kernel do host.

6.1.1Arquitetura: VMs vs. contentores

O motor (engine) isola e configura os recursos:

  • Os contentores estão isolados entre si: o host fica compartimentado em CPU, RAM e disco.
  • Cada contentor partilha o hardware e o kernel/SO com o host. É daqui que vem tanto a leveza como a menor segurança face às VMs.

6.1.2Blocos de construção

Os contentores não são uma peça única: assentam em componentes do kernel Linux.

ComponenteFunçãoO que faz
NamespacesIsolamentoDividem recursos do host (rede, sistema de ficheiros…) em recursos dedicados, acessíveis só a um grupo de processos. Respondem a "o que é que o contentor vê?"
Control groups (cgroups)Gestão de recursosDistribuem CPU, RAM, disco e rede por grupos de processos e limitam o que cada contentor pode usar. Respondem a "quanto é que o contentor pode gastar?"
SELinuxSegurançaImpõe controlo de acessos e políticas de segurança, para lá dos namespaces, para um contentor não comprometer o host nem os outros contentores.
Exemplo

Dois contentores podem ter ambos um servidor na porta 80, porque cada um tem o seu namespace de rede. Se um deles tiver um limite de 512 MB no cgroup, não consegue esgotar a RAM do host.

6.1.3Tipos de contentores

Contentores de SO

Ex.: LXC. Correm vários processos e simulam um sistema operativo "leve".

Contentores de aplicação

Ex.: Docker. Focados em instalar aplicações, cada uma vista como um processo independente.

Docker

A plataforma de contentores mais conhecida. Suporta Ubuntu, Fedora, RHEL, CentOS, Windows, entre outros.

6.2.1Cliente, daemon e objetos

PeçaPapel
Docker ClientÉ por onde o utilizador interage com a plataforma. Usa a API do Docker para correr e gerir contentores, gerir redes e volumes, ler logs e métricas, descarregar e gerir imagens.
Docker DaemonRecebe os pedidos do cliente pela API e gere imagens, contentores, volumes e redes.
ImagemFicheiro imutável com o código, as bibliotecas e os restantes ficheiros de que a aplicação precisa para correr.
ContentorInstância em execução de uma imagem.
Registo (registry)Repositório de imagens, ex.: Docker Hub.
Imagem vs. contentor

A relação é a de uma classe e dos seus objetos: da mesma imagem podem sair muitos contentores, e alterar um deles não muda a imagem.

docker pull nginx:1.27                        # descarrega a imagem do registo
docker run -d --name web -p 8080:80 nginx:1.27  # cria e arranca um contentor
docker ps                                     # lista os contentores em execução
docker logs web                               # lê os logs
docker stop web && docker rm web              # para e remove o contentor
Construir a própria imagem complemento

Uma imagem descreve-se num Dockerfile e constrói-se com docker build -t app:1.0 .. Cada instrução cria uma camada reutilizável, por isso copiar primeiro a lista de dependências evita reinstalá-las sempre que o código muda.

FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install -r requirements.txt
COPY . .
CMD ["python", "app.py"]

6.2.2Volumes: guardar dados

O sistema de ficheiros interno de um contentor é efémero: os dados desaparecem quando o contentor é removido. Para os manter, monta-se um ficheiro ou diretório do host, independente do contentor.

Bind mount

Um diretório qualquer do host. Tanto os contentores como os processos do host lhe podem aceder.

Volume

Um diretório especial do host, gerido pelo Docker e destinado apenas a ser acedido por contentores.

docker volume create dados
docker run -d --name bd -e POSTGRES_PASSWORD=segredo \
  -v dados:/var/lib/postgresql/data postgres:16   # volume
docker rm -f bd                                   # remove o contentor; o volume fica

docker run -d --name web -v "$PWD/site:/usr/share/nginx/html" nginx:1.27   # bind mount

6.2.3Redes

Host

O contentor partilha o namespace de rede do host. Os seus serviços aparecem na rede como se fossem do próprio host, e as portas são partilhadas (ex.: só um serviço pode usar a porta 80).

Bridge

O contentor tem o seu próprio endereço e é visto como mais um nó da rede.

A bridge por omissão complemento

Na configuração habitual do Docker, essa rede é uma bridge virtual privada dentro do host (ex.: 172.17.0.0/16), diferente do modo bridge das VMs. Os contentores falam entre si, mas de fora só se chega a eles publicando portas (-p 8080:80). Para um contentor aparecer diretamente na rede física existe o driver macvlan.

Kubernetes: o clusterKubernetes (K8s)

O Docker gere contentores num servidor. O Kubernetes é uma plataforma de orquestração: automatiza a instalação, o escalamento e a gestão de contentores em muitos servidores.

6.3.1O que oferece

  • Escalonamento, auto-recuperação (self-healing) e escalamento de contentores, simplificados e automáticos.
  • Gestão de rede: descoberta de serviços e balanceamento de carga.
  • Orquestração modular de armazenamento: iSCSI, NFS, Ceph, AWS, GCP…

6.3.2Componentes

Um cluster é formado por um Control Plane e um conjunto de nós. Os nós alojam os Pods, que correm as aplicações em contentores; o Control Plane gere os nós, a rede, o armazenamento e os Pods.

OndeComponenteO que faz
Control PlaneAPI ServerO servidor central, que expõe a API HTTP do Kubernetes.
etcdBase de dados chave-valor com a configuração e o estado do cluster.
SchedulerDistribui os Pods ainda sem nó pelos nós disponíveis.
Controller ManagerCorre os controladores (ex.: de replicação, de namespaces) que implementam o comportamento da API.
NóKubeletGere os contentores de acordo com as especificações dos Pods que recebe.
Kube-proxyAceita e controla as ligações de rede para os Pods do nó.
Container runtimeO software que corre os contentores (ex.: Docker).
O runtime hoje complemento

Desde a versão 1.24, o Kubernetes já não inclui suporte direto ao Docker Engine: os clusters usam normalmente containerd ou CRI-O. As imagens construídas com Docker continuam a funcionar, porque seguem o mesmo formato (OCI).

Em que parte do cluster está?

Decidir em que servidor fica um novo Pod
Arrancar os contentores descritos na especificação de um Pod
Guardar o estado do cluster
Encaminhar uma ligação de rede para um Pod desse servidor
Receber os pedidos do kubectl

6.3.3Como se usa

  • O administrador monta o cluster com o kubeadm: kubeadm init para o inicializar e kubeadm reset para o destruir.
  • Os clientes interagem com o cluster, através do Control Plane, usando o kubectl.

O fluxo é declarativo: descreve-se o que se quer, não os passos para lá chegar.

  1. Submete-se um ficheiro de configuração YAML a descrever o que se pretende.
  2. O Control Plane valida-o e guarda o estado no etcd.
  3. O Scheduler atribui os Pods aos nós.
  4. O Kubelet garante que esses Pods estão a correr.
  5. O Controller Manager mantém tudo sincronizado, de forma automática.

Pods e DeploymentsKubernetes Workloads

Um workload é uma aplicação a correr no Kubernetes. Seja um só componente ou vários a trabalhar em conjunto, corre sempre dentro de um conjunto de Pods.

6.4.1Pod

Um Pod é um grupo de um ou mais contentores, com armazenamento e rede partilhados e uma especificação de como os correr. É a menor unidade que se pode instalar no Kubernetes: não se instala um contentor isolado.

6.4.2Deployment e ReplicaSet

Deployment

Forma declarativa de gerir e escalar um conjunto de Pods idênticos (réplicas). Define o estado desejado (ex.: quantas réplicas) e gere o ciclo de vida dos Pods.

ReplicaSet

Garante que está a correr, em cada momento, o número indicado de réplicas. O Deployment é um conceito de nível superior, que gere automaticamente os ReplicaSets.

Na prática, escreve-se o Deployment; a hierarquia é Deployment → ReplicaSet → Pods.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3                # estado desejado
  selector:
    matchLabels:
      app: web
  template:                  # modelo dos Pods
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: nginx
          image: nginx:1.27
          ports:
            - containerPort: 80
kubectl apply -f web-deployment.yaml      # submete o estado desejado
kubectl get pods                          # vê os Pods criados
kubectl scale deployment web --replicas=5 # altera o estado desejado
A ideia a reter

O Kubernetes compara continuamente o estado desejado com o estado real e corrige a diferença. A auto-recuperação não é um mecanismo à parte: um Pod que morre é só uma diferença a corrigir.

Rede, armazenamento e configuraçãoNetwork, Storage and Configuration

Os Pods são substituídos a qualquer momento. Por isso, é preciso um ponto de acesso estável para os alcançar e um sítio para os dados que tenha de sobreviver a cada Pod.

6.5.1Rede de Pods

Cada Pod tem um endereço IP único em todo o cluster. A comunicação entre Pods, mesmo em nós diferentes, é assegurada por uma rede overlay (ex.: Flannel, Calico).

6.5.2Services

Um Service é uma abstração, construída sobre a overlay, para expor um grupo de Pods na rede. Define um conjunto lógico de destinos (ex.: Pods) e uma política de acesso. Assim, quem usa o serviço não precisa de conhecer os IPs dos Pods, que mudam quando estes são recriados.

TipoExpõe o serviço…Uso típico
ClusterIPnum IP interno do clusterComunicação interna, ex.: a aplicação web a falar com a base de dados
NodePortno IP de cada nó, numa porta estáticaAcesso externo simples
LoadBalancerexternamente, com um balanceador de carga externoProdução, em cloud
apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  type: NodePort
  selector:
    app: web          # encaminha para os Pods com esta etiqueta
  ports:
    - port: 80        # porta do Service
      targetPort: 80  # porta do contentor
      nodePort: 30080 # porta aberta em cada nó

6.5.3Armazenamento

Os Pods acedem a volumes de vários backends (iSCSI, NFS, AWS, GCP…), que podem ser:

  • Efémeros: disponíveis durante a vida do Pod.
  • Persistentes: continuam disponíveis mesmo depois de o Pod terminar.
ObjetoO que éQuem o cria
PersistentVolume (PV)Um pedaço de armazenamento do clusterO administrador, ou dinamicamente através de uma Storage Class
PersistentVolumeClaim (PVC)O pedido de armazenamento para um Pod. Liga-se a um PVO programador da aplicação
Storage Class (SC)Descreve os tipos de armazenamento disponíveis (mais rápido/lento, local/remoto)O administrador
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: dados
spec:
  accessModes:
    - ReadWriteOnce
  storageClassName: rapido    # tipo de armazenamento pedido
  resources:
    requests:
      storage: 10Gi
Porquê PV e PVC separados?

Separa os papéis: quem escreve a aplicação pede "10 GiB rápidos" sem saber onde estão; quem administra o cluster decide o que há por baixo.

6.5.4ConfigMaps e Secrets

ConfigMap

Guarda e atualiza a configuração não confidencial dos Pods, em pares chave-valor (ex.: variáveis de ambiente, argumentos da linha de comandos).

Secret

Guarda os dados confidenciais dos Pods (ex.: palavras-passe, tokens, chaves).

Ambos permitem usar a mesma imagem em vários ambientes, sem pôr configuração nem credenciais dentro dela.

env:
  - name: DB_HOST
    valueFrom:
      configMapKeyRef:
        name: app-config
        key: db_host
  - name: DB_PASSWORD
    valueFrom:
      secretKeyRef:
        name: app-secrets
        key: db_password
Um Secret não é cifrado por omissão complemento

Por omissão, os valores estão apenas codificados em base64 e guardados sem cifra no etcd: quem tiver acesso ao etcd ou permissão de leitura sobre o Secret consegue lê-los. Em produção, ativa-se a cifra em repouso e restringe-se o acesso com RBAC. E um Secret nunca deve ir para o repositório Git.

Contentores vs. VMsContainers vs. VMs

Cada tecnologia foi feita com objetivos diferentes: nenhuma é sempre melhor, a escolha depende do caso de uso.

6.6.1Quando usar cada um

VMs

Quando é preciso virtualizar um servidor completo, com o seu SO.

Contentores

Para gerir ambientes virtuais com bibliotecas e aplicações heterogéneas.

6.6.2Vantagens e desvantagens

Contentores face às VMsPorquê
+Teste, provisionamento e migração mais rápidosSão mais leves
+Melhor utilização de recursos e melhor desempenhoNão há um SO convidado por instância
+Instalam-se facilmente em servidores físicos e virtualizadosUma VM dentro de outra VM exige virtualização aninhada, que só alguns hypervisors suportam
−Isolamento e segurança mais fracosO SO e o kernel são partilhados
−Menos flexibilidade para correr SOs diferentes (Linux, Windows, BSD…)Pela mesma razão: há um só kernel

VM ou contentor?

Correr uma aplicação que só funciona em Windows num servidor Linux
Correr duas versões da mesma base de dados no mesmo servidor, para testes
Alojar, no mesmo host, código de clientes que não confiam uns nos outros
Lançar dezenas de instâncias em segundos para responder a um pico de carga
Não são alternativas exclusivas

É comum usar os dois: na cloud, os nós de um cluster Kubernetes são muitas vezes VMs, e os contentores correm dentro delas.

Erros comuns
  • Pensar que um contentor traz o seu próprio kernel. Traz bibliotecas, mas o kernel é o do host.
  • Guardar dados só no sistema de ficheiros interno do contentor: perdem-se quando este é removido.
  • Confundir o papel do Scheduler (decide onde) com o do Kubelet (faz correr).
  • Ligar a aplicação diretamente ao IP de um Pod: muda quando o Pod é recriado. Usa-se um Service.

Σ.2Perguntas de escolha múltipla

Qual é a razão fundamental para os contentores serem mais leves do que as VMs?

Não há um SO completo por instância. É também por isso que o isolamento é mais fraco.

Um contentor não pode usar mais de 2 núcleos e 1 GB de RAM. Que mecanismo do kernel o garante?

Os cgroups limitam recursos; os namespaces isolam o que cada contentor vê.

Removes um contentor de base de dados que guardava tudo no seu sistema de ficheiros interno. O que acontece aos dados?

Para persistir é preciso montar um volume ou um bind mount. A imagem é imutável.

O que é uma imagem Docker?

A instância em execução é o contentor; o repositório de imagens é o registo.

Qual é a menor unidade que se pode instalar no Kubernetes?

Um Pod agrupa um ou mais contentores, que partilham rede e armazenamento.

Um Deployment pede 3 réplicas e um dos Pods morre. O que acontece?

O ReplicaSet mantém o número de réplicas e o Scheduler coloca o novo Pod num nó.

Que componente escolhe o nó onde um novo Pod vai correr?

O Scheduler decide; depois, o kubelet desse nó põe o Pod a correr. O etcd guarda o estado.

A aplicação web tem de falar com a base de dados dentro do cluster, sem a expor para fora. Que tipo de Service usas?

O ClusterIP só é acessível dentro do cluster; os outros dois expõem o serviço para o exterior.

Quem usa um PersistentVolumeClaim (PVC)?

O PVC é o pedido, o PV é o armazenamento e a Storage Class descreve os tipos disponíveis.

Onde deves guardar a palavra-passe da base de dados de uma aplicação em Kubernetes?

Os ConfigMaps são para configuração não confidencial; a imagem é partilhada e não deve conter credenciais.

Qual destas é uma desvantagem dos contentores face às VMs?

As outras duas são precisamente vantagens dos contentores.

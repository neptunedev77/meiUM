Aplicações DistribuídasDistributed Applications

Porque é que uma aplicação se espalha por vários servidores, e de que formas o pode fazer. Duas perguntas: porquê distribuir? e como distribuir?

2.0.1Porquê distribuir

Modularidade

Desacoplar componentes com preocupações diferentes: armazenamento, base de dados, servidor aplicacional, servidor web.

Desempenho e escalabilidade

Mais servidores a fazer o trabalho significa mais capacidade.

Disponibilidade e fiabilidade

O hardware e o software falham com frequência; com vários servidores, a falha de um não tem de parar o serviço.

⌁Mapa do tema

Baseado nas aulas de ASCN (Distributed Applications). Caixas e etiquetas complemento vão além da matéria dada na aula.

Do sistema monolítico à escalaMonolithic system · Challenges

Num sistema monolítico, vários componentes (armazenamento, base de dados, servidor aplicacional) servem vários alvos (por exemplo, os dados de clientes diferentes) no mesmo servidor.

2.1.1Dois problemas

E se o servidor não aguentar a carga dos clientes?

  • Scale-up (escalar na vertical): aumentar os recursos do servidor — mais CPU, RAM, disco.
  • Scale-out (escalar na horizontal): aumentar o número de servidores.

E se o servidor falhar?

  • Redundância: ter servidores redundantes, prontos a assumir o trabalho.

Replicação, partição e SOADistribution patterns

Os principais mecanismos de distribuição são três. Todos servem o scale-out; só a replicação dá também redundância. Não são exclusivos: combinam-se.

Exemplo: uma aplicação com três camadas (armazenamento, base de dados, servidor aplicacional) que guarda os dados de três clientes, A, B e C.

2.2.1Replicação

Várias cópias dos mesmos dados e/ou da mesma funcionalidade, mantidas sincronizadas.

Servidor 1Servidor 2
Armazenamento, BD, aplicaçãoA, B, CA, B, C
  • Fiabilidade: se o servidor 1 falhar, o servidor 2 faz o seu trabalho.
  • Scale-out: os pedidos de leitura repartem-se pelos dois.

2.2.2Partição (sharding)

O servidor é dividido na horizontal: cada servidor fica com uma parte dos dados e/ou da computação.

Servidor 1Servidor 2Servidor 3
Armazenamento, BD, aplicaçãoABC
  • Scale-out: o servidor 1 trata dos dados e pedidos do cliente A, o 2 do B, e assim por diante. Não há redundância: se o servidor 2 falhar, os dados de B ficam indisponíveis.

2.2.3Arquitetura orientada a serviços (SOA)

O servidor é dividido na vertical (por exemplo, em microsserviços): cada servidor fica com uma funcionalidade, para todos os dados.

Combinar

O caso típico: particionar os dados por vários servidores para escalar e replicar cada partição para tolerar falhas.

Do monólito aos microsserviçosMonolithic to Microservices

Numa arquitetura de microsserviços, a aplicação é partida em serviços pequenos, cada um com uma funcionalidade específica, que comunicam entre si pela rede.

Vantagem

Cada serviço implementa uma funcionalidade específica e escala de forma independente: se o serviço de pagamentos estiver sobrecarregado, acrescentam-se instâncias só desse.

Dificuldades
  • Decomposição: quão "micro" é micro? Devo partir mais as funcionalidades?
  • Consistência: como garantir que os dados estão consistentes entre todos os serviços?
  • Deployment e testes complexos: muitos serviços, muitas versões, muitas interações.
Complemento · porque é que o DevOps importa aqui

Com dezenas de serviços, instalar e configurar à mão é impraticável. Os microsserviços só são viáveis com a automação do tema 1 e do tema 3.

Arquiteturas distribuídasDistributed architectures

Os mecanismos anteriores dizem o que se distribui; as arquiteturas dizem como os componentes se organizam e comunicam para o permitir.

2.4.1Cliente-servidor

  • A funcionalidade e os dados estão no servidor.
  • Um stub corre embutido no cliente: dá uma API para interagir com o servidor e esconde os detalhes do protocolo. Faz parte do pacote de software do servidor.
  • Exemplo: a Web, em que o protocolo é HTTP.
  • Com um só servidor, não há escalabilidade nem fiabilidade.

2.4.2Proxy-servidor

  • O proxy abstrai a interação com vários servidores: bom para replicação e/ou sharding transparentes.
  • O proxy pode ser um gargalo de escalabilidade e disponibilidade: ponto único de contenção e de falha.
  • Exemplo: MongoDB.
StubProxy
Onde estáNo clienteEntre o cliente e os servidores, por baixo do protocolo
O que torna transparenteO protocoloOs servidores (quantos são, onde estão os dados)

Os dois podem combinar-se: o cliente usa um stub para falar com o proxy.

2.4.3Manager-worker

  • A funcionalidade divide-se entre um manager (trata da localização dos ficheiros: os metadados) e vários workers (tratam do conteúdo: os dados).
  • Os dados podem ser replicados e/ou particionados pelos workers.
  • Escala melhor, porque divide a funcionalidade — mas o manager continua a poder ser um ponto único de contenção e de falha.
  • Comum em sistemas de armazenamento: HDFS, Lustre…

2.4.4Grupo de servidores

  • Todos os servidores podem atender e processar pedidos: a falha de um não compromete dados nem funcionalidade.
  • Um protocolo de sincronização garante a replicação e consistência do estado entre servidores — exige coordenação.
  • Sem pontos únicos de falha, mas a coordenação torna mais difícil escalar.
  • Exemplo: ZooKeeper.

2.4.5Bus

  • O bus encaminha mensagens: os participantes publicam e consomem mensagens usando um protocolo.
  • Desacopla produtores de consumidores → mais flexibilidade: um cliente pode consumir umas mensagens e produzir outras, e é fácil acrescentar novos participantes.
  • Exemplo: Apache Kafka.

2.4.6Multi-camada (multi-tier)

  • Cada servidor atua como cliente da camada seguinte: cliente-servidor encadeado.
  • Permite instalar e escalar de forma independente cada funcionalidade.
  • Exemplo: o protocolo A é a Web; o "stub B" é o driver da base de dados; o protocolo B é SQL.

Estado em multi-camada e combinaçõesState in multi-tier · Final remarks

Numa aplicação multi-camada, o estado (os dados que têm de sobreviver entre pedidos) não está espalhado por igual.

CamadaEstado típico
Superior: servidor webSem estado (stateless) — só computação
Intermédia: servidor aplicacionalEstado transitório ou em cache
Inferior: base de dadosEstado persistente

É o caso típico, não uma regra.

Que camadas é preciso considerar para garantir disponibilidade?

Todas. Se qualquer camada tiver um só servidor, a sua falha para a aplicação inteira. Mas o esforço é diferente: nas camadas sem estado basta pôr mais instâncias; na camada com estado persistente é preciso replicar os dados.

Porque é que a computação é mais fácil de replicar e particionar do que o estado persistente?

Um servidor sem estado é intercambiável: qualquer réplica pode atender qualquer pedido, e não há nada a sincronizar entre réplicas. Com estado persistente, cada escrita tem de chegar a todas as réplicas (ou à partição certa) e é preciso garantir que todas ficam consistentes — exatamente a coordenação que torna o grupo de servidores difícil de escalar.

2.5.1Combinar tudo

Os padrões, mecanismos e arquiteturas combinam-se para cumprir requisitos de desempenho, escala e fiabilidade:

  • Os dados são particionados por vários servidores para escalar, e cada partição é replicada para tolerar falhas.
  • Os componentes proxy e manager podem seguir eles próprios uma arquitetura de grupo de servidores, para deixarem de ser pontos únicos de falha e de contenção.
  • Cada camada de uma aplicação multi-camada pode seguir a sua própria arquitetura e os seus próprios mecanismos de distribuição.

Σ.2Perguntas de escolha múltipla

Qual dos mecanismos dá também redundância (tolerância a falhas)?

Só a replicação mantém várias cópias: se um servidor falhar, outro tem os mesmos dados.

Dividir os clientes A–M para o servidor 1 e N–Z para o servidor 2 é…

Divisão horizontal dos dados: cada servidor tem uma parte.

Qual é a diferença entre um stub e um proxy?

O stub está no cliente e dá uma API; o proxy fica no meio e torna transparente a replicação/sharding.

Num sistema manager-worker como o HDFS, o manager guarda…

Os workers guardam os dados; o manager sabe onde estão. Por isso pode ser um ponto único de falha.

Qual arquitetura não tem ponto único de falha, mas escala com mais dificuldade?

Todos os servidores atendem, mas o protocolo de sincronização exige coordenação entre todos.

Porque é que é mais fácil replicar um servidor web do que uma base de dados?

Réplicas sem estado são intercambiáveis; com estado, cada escrita tem de ser sincronizada.

Provisionamento de SistemasSystem Provisioning

Como passar da infraestrutura como código (tema 1) à prática: descrever a configuração de dezenas de máquinas em ficheiros versionados e aplicá-la com uma ferramenta — aqui, o Ansible.

3.0.1O fluxo de trabalho

Na máquina de quem administra estão as receitas, guardadas num repositório (ex.: Git). A ferramenta envia-as por SSH/SCP para cada servidor — web, email, base de dados — e aplica-as.

Provisionamento e deploymentProvisioning · Deployment

Dois termos próximos, com âmbitos diferentes.

Provisionamento

A ação de fornecer algo para ser usado.

Provisionamento de servidores, de armazenamento, de rede, de VMs, de utilizadores.

Deployment

O processo de instalar ou atualizar uma aplicação/serviço num servidor.

Instalar ou atualizar uma aplicação web; instalar um serviço de rede. O âmbito é o serviço ou a aplicação.

Gestão de configuraçãoConfiguration Management

Uma forma de lidar com alterações sistemáticas a um sistema mantendo a sua integridade ao longo de todo o ciclo de vida.

  • Exprimir a configuração num dialeto comum: cada unidade de trabalho é uma receita. Bónus: a infraestrutura fica documentada.
  • Combinar com um sistema de controlo de versões (ex.: Git): a configuração evolui com a infraestrutura e fica o histórico completo das alterações.

3.2.1Receitas

Uma receita define a automação de uma tarefa através de diretivas numa dada linguagem. A forma mais simples é um script de shell:

#!/bin/sh
username=deployer
apt-get -y update
apt-get -y upgrade
apt-get -y install vim-nox openntpd sudo whois aptitude
useradd -G sudo -p "password" -s /bin/bash -m $username
mkdir -p /home/$username/.ssh
chmod 700 /home/$username/.ssh
chown $username: /home/$username/.ssh
echo "public_key" >> /home/$username/.ssh/authorized_keys
chmod 600 /home/$username/.ssh/authorized_keys
chown $username: /home/$username/.ssh/authorized_keys
O problema do script

Corrido uma segunda vez, o useradd falha (o utilizador já existe) e o echo >> acrescenta a chave outra vez. Um script descreve passos, não um estado. As ferramentas de gestão de configuração resolvem isto com a idempotência (3.3).

Agente vs. sem agente

Com agente, cada servidor gerido corre um programa da ferramenta, que recebe ou vai buscar a configuração. Sem agente (o caso do Ansible), basta que o servidor aceite ligações SSH e tenha Python: não há nada para instalar nem manter nos hosts.

AnsibleAnsible

O Ansible é uma ferramenta de automação open-source usada para gestão de configuração, deployment de aplicações, orquestração de serviços e provisionamento.

3.3.1Vocabulário

TermoO que é
InventárioOs alvos do deployment (hosts), agrupados.
MóduloUnidade de trabalho reutilizável, distribuída com o Ansible ou desenvolvida para ele (apt, user, copy, service…).
TarefaUm módulo com argumentos, que cria uma ação ("instalar o nginx").
HandlerTarefa especial que só corre quando é notificada (ex.: reiniciar um serviço quando a configuração muda).
TemplateFicheiro de configuração dinâmico, escrito em Jinja2 (o motor de templates do Python).
RoleComponente reutilizável que agrupa variáveis, templates, tarefas, handlers… (configurável).
PlaybookDescreve as políticas a impor nos sistemas remotos: um conjunto de roles e/ou tarefas aplicadas a grupos de hosts.

3.3.2Como funciona

  1. O Ansible é operado a partir de um nó de gestão (management node), onde se escrevem e executam os playbooks.
  2. A lista de hosts geridos está no ficheiro de inventário, organizada em grupos.
  3. O Ansible liga-se aos hosts remotos por SSH e executa as roles/tarefas definidas no playbook.
  4. As tarefas só fazem alterações se o estado do alvo for diferente do esperado — idempotência.

As receitas escrevem-se em YAML, com módulos e tarefas, organizadas em roles e playbooks.

Porque é que a idempotência importa

Pode-se correr o mesmo playbook sempre que se quiser: num servidor novo configura tudo; num servidor já configurado não muda nada; num servidor que divergiu, corrige só o que divergiu. É isto que combate o configuration drift do tema 1.

Inventário e playbooksInventory · Playbooks · Execution

Os três ficheiros que se escrevem sempre: o inventário (onde), o playbook (o quê) e, opcionalmente, o ansible.cfg (como ligar).

3.4.1Inventário

[webservers]
host-[01:99].example.com

[database]
db-01.example.com
staging.example.com

Os grupos entre parênteses retos podem ser usados como alvo dos playbooks. host-[01:99] é uma abreviatura para 99 hosts.

3.4.2Um playbook simples

O mesmo que o script de shell de 3.2 — criar um utilizador e autorizar a sua chave SSH — mas declarado como estado desejado:

- hosts: all
  vars:
    username: someuser
    shell: /bin/bash
  tasks:
    - name: create unprivileged user
      user:                                  # módulo
        name: "{{ username }}"
        password: "secretpasswordhash"
        shell: "{{ shell }}"

    - name: set SSH authorized key
      authorized_key:                        # módulo
        user: "{{ username }}"
        state: present
        key: "{{ lookup('file', '/home/' + username + '/.ssh/id_rsa.pub') }}"
  • hosts: a que hosts (ou grupos do inventário) se aplica.
  • vars: variáveis, usadas com {{ … }} (Jinja2).
  • Cada tarefa tem um name e um módulo com os seus argumentos.
  • state: present descreve o estado final, não a ação: se a chave já lá está, nada acontece.

3.4.3Estrutura com roles

hosts.inv
provision.yml
roles/
 └─ role/
    ├─ files/      ficheiros estáticos
    ├─ templates/  templates Jinja2
    ├─ tasks/      main.yml: as tarefas
    ├─ handlers/   main.yml: handlers
    ├─ vars/       main.yml: variáveis da role
    └─ …           defaults, meta…
- hosts: webservers
  roles:
    - config
    - users
    - ssh-server
    - ntp-client

Cada role é reutilizável entre projetos. Há exemplos no repositório oficial ansible/ansible-examples.

3.4.4Executar

ansible-playbook playbook.yml -b -i hosts.inv -u someuser -K --private-key=/path/to/private_key
OpçãoSignificado
-bbecome: elevar privilégios com sudo
-ificheiro de inventário a usar
-uutilizador com que se faz login
-Kpedir a password de sudo

Com um ansible.cfg na pasta do projeto, as opções repetidas passam para lá e o comando encurta para ansible-playbook playbook.yml -b -K:

[defaults]
inventory = hosts.inv
remote_user = someusername
private_key_file = /path/to/someuser_private_key

Em versões antigas do Ansible a primeira chave chamava-se hostfile; hoje é inventory.

Subir de nívelLevel up

As construções que tornam os playbooks dinâmicos, seguros e capazes de criar a própria infraestrutura.

3.5.1Handlers

Uma tarefa pode notificar um handler; o handler só corre se a tarefa tiver feito alterações (e uma só vez, no fim).

tasks:
  - name: template configuration file
    template:
      src: template.j2
      dest: /etc/nginx/nginx.conf
    notify:
      - restart nginx

handlers:
  - name: restart nginx
    service:
      name: nginx
      state: restarted

3.5.2Condições

- name: Common Debian
  include_tasks: debian.yml
  when: ansible_os_family == "Debian"

- name: Common RedHat
  include_tasks: rh.yml
  when: ansible_os_family == "RedHat"

Outras formas: uma lista de condições (todas têm de se verificar), when: a or b, when: somevar is defined, when: somevar is failed.

3.5.3Ciclos

- name: Install packages
  apt:
    name: "{{ item }}"
    update_cache: yes
    state: latest
  loop:
    - vim-nox
    - aptitude            # ou: loop: "{{ list_variable_with_packages }}"

- name: Copy files
  copy:
    src: "{{ item.source }}"
    dest: "{{ item.destination }}"
  loop:
    - { source: 'motd', destination: '/etc/motd' }
    - { source: 'sshd', destination: '/etc/ssh/sshd_config' }

3.5.4Facts

Antes de correr as tarefas, o Ansible recolhe facts sobre cada host (distribuição, família do SO, número de CPUs, endereços IP…). Podem usar-se em tarefas e templates:

{% for host in groups['webservers'] %}
  {{ hostvars[host]['ansible_all_ipv4_addresses'] | join }}
{% endfor %}

{{ ansible_distribution }}  {{ ansible_os_family }}  {{ ansible_processor_vcpus }}

Exemplo típico: gerar a configuração de um balanceador de carga com os IPs de todos os servidores web.

3.5.5Vault

O Ansible Vault guarda dados sensíveis — passwords, chaves — em ficheiros cifrados, em vez de os deixar em claro nos playbooks ou roles (que vão para o Git).

ansible-vault create secrets.yml           # cria um ficheiro cifrado
ansible-playbook site.yml --ask-vault-pass # pede a password para o decifrar

3.5.6Provisionar a própria infraestrutura na cloud

O Ansible também cria recursos, não só os configura. Na Google Cloud Platform há módulos como gcp_compute_disk, gcp_compute_network, gcp_compute_address, gcp_compute_firewall, gcp_compute_instance e gcp_container_cluster (VMs, redes, Kubernetes…).

Inventário dinâmico

Quando as máquinas são criadas dinamicamente, os seus endereços não se conhecem de antemão. Duas soluções: manual (ir à consola ver os endereços e escrevê-los no inventário) ou automática, com um inventário dinâmico que pergunta ao fornecedor de cloud que máquinas existem.

Σ.2Perguntas de escolha múltipla

O que significa que o Ansible é "sem agente"?

Chef, Puppet e SaltStack usam normalmente um agente em cada host; o Ansible liga-se por SSH.

Corre-se o mesmo playbook duas vezes seguidas num servidor. Na segunda execução…

Idempotência: as tarefas só agem quando o estado atual difere do esperado.

Quando corre um handler?

Ex.: reiniciar o nginx só se o ficheiro de configuração tiver mudado.

O que faz a opção -b do ansible-playbook?

-i é o inventário, -u o utilizador, -K pede a password de sudo.

Onde se devem guardar passwords usadas num playbook?

O Vault cifra os segredos para que possam ser versionados sem ficarem expostos.

Para que serve um inventário dinâmico?

Quando as VMs são criadas pelo próprio playbook, os IPs só se conhecem depois.
